# T2.10 — MSVC: restore upstream's `<memory>` for vendored `util/guarded_allocator.h`, and a Windows C++ CI job
Milestone: M2 · Depends on: T3.12, TQ.1 · Parallel-safe: no

## Goal
The second dispatch of `.github/workflows/wheels.yml` (run 37984431443, commit `d2259e7`) built the Linux and macOS wheels,
and the macOS coexist job passed. The Windows wheel failed to compile `cycles_util`. Two translation units
(`third_party/cycles/util/aligned_malloc.cpp`, `third_party/cycles/util/guarded_allocator.cpp`) stop at
`third_party/cycles/util/guarded_allocator.h:126-131`:
```
error C2039: '_Container_proxy': is not a member of 'std'
error C2039: 'allocator': is not a member of 'std'
```

Cause:
- Lines 108-134 of the header are an `#ifdef _MSC_VER` block that names `std::_Container_proxy` and `std::allocator`. Both are
  declared in MSVC's `<xmemory>`, which `<memory>` includes.
- The header itself includes only `<cstddef>`, `<cstdlib>` and `<new>`. Both failing sources include it first.
- Upstream compiles every Cycles source with `WITH_BLENDER_GUARDEDALLOC` (Blender v5.2.2 `intern/cycles/CMakeLists.txt:382`).
  Line 12 of the header then includes `MEM_guardedalloc.h`, and that includes `<memory>` (its line 297) before line 108 is
  reached.
- We do not link Blender's guardedalloc, so that include is missing. GCC and Clang never compile the `_MSC_VER` block, which
  is why Linux and macOS build.

The fix restores the include environment upstream relies on. `third_party/` stays verbatim (CLAUDE.md rule 1). A shim is not
allowed either, because shims never wrap the vendored header (docs/architecture.md).

The wheel job is the only MSVC build today. It takes about an hour, and it stops at the first library that fails, so the code
of T3.3-T3.12 has never been compiled by MSVC. This card therefore also adds a Windows job to `ci.yml`. The job builds the
C++ libraries and unit tests with MSVC and Ninja, and runs them on every push.

## Read first
- `src/cycles/CMakeLists.txt` (the existing per-compiler blocks: the SSE flags and `-Wno-invalid-offsetof`).
- `third_party/cycles/util/guarded_allocator.h` (lines 1-15 and 108-134).
- `.github/workflows/ci.yml` and `.github/workflows/wheels.yml` (how the Embree source is cached and passed with
  `FETCHCONTENT_SOURCE_DIR_EMBREE`).
- Root `CMakeLists.txt` (the options `PAINTERLY_BUILD_MODULE`, `PAINTERLY_BUILD_TESTS`, `PAINTERLY_BUILD_ORACLE`; the static
  CRT; `/fp:precise`).

## Modify
1. `src/cycles/CMakeLists.txt`. Directly after the `target_compile_definitions(cycles_util PUBLIC ...)` call for
   `CCL_NAMESPACE_BEGIN`/`END`, add:
   ```cmake
   # MSVC: util/guarded_allocator.h:108-134 (#ifdef _MSC_VER) names std::_Container_proxy and std::allocator, but the
   # header includes only <cstddef>, <cstdlib> and <new>. Upstream compiles Cycles with WITH_BLENDER_GUARDEDALLOC
   # (Blender v5.2.2 intern/cycles/CMakeLists.txt:382), so the header's MEM_guardedalloc.h include brings in <memory>
   # (MEM_guardedalloc.h:297) first. We do not link Blender's guardedalloc, so <memory> is force-included instead. The
   # option is PUBLIC because any consumer may include the header before <memory>. GCC and Clang never compile the block.
   if(MSVC)
     target_compile_options(cycles_util PUBLIC /FImemory)
   endif()
   ```
   CMake sets `MSVC` for `cl` and for `clang-cl`, which are exactly the compilers that define `_MSC_VER`.
2. `.github/workflows/ci.yml`. Change the header comment to: `# Continuous integration (T0.4, T2.10): lint, build and test
   on Linux; build and unit-test the C++ libraries with MSVC on Windows.` Then add a second job, `windows`, after `linux`:
   ```yaml
     # MSVC builds what the wheel compiles (cycles_*, painterly_*, Embree) plus the doctest unit tests, with Ninja so that
     # Embree compiles in parallel. The module itself is built and audited by wheels.yml.
     windows:
       runs-on: windows-2022
       steps:
         - name: Check out the repository
           uses: actions/checkout@v4

         - name: Cache the Embree source
           id: embree-src
           uses: actions/cache@v4
           with:
             path: .cache/src/embree
             key: embree-src-${{ hashFiles('cmake/painterly_embree.cmake') }}

         - name: Clone the Embree source
           if: steps.embree-src.outputs.cache-hit != 'true'
           shell: bash
           run: git clone --depth 1 --branch v4.4.1 https://github.com/RenderKit/embree.git .cache/src/embree

         - name: Build the C++ libraries and unit tests with MSVC
           shell: cmd
           run: |
             for /f "usebackq tokens=*" %%i in (`"%ProgramFiles(x86)%\Microsoft Visual Studio\Installer\vswhere.exe" -latest -property installationPath`) do set "VSROOT=%%i"
             call "%VSROOT%\VC\Auxiliary\Build\vcvars64.bat" || exit /b 1
             cmake --version || exit /b 1
             ninja --version || exit /b 1
             cmake -S . -B build/msvc -G Ninja -DCMAKE_BUILD_TYPE=Release -DPAINTERLY_BUILD_MODULE=OFF -DPAINTERLY_BUILD_TESTS=ON -DPAINTERLY_BUILD_ORACLE=OFF -DFETCHCONTENT_SOURCE_DIR_EMBREE=.cache/src/embree || exit /b 1
             cmake --build build/msvc || exit /b 1

         - name: Run the C++ unit tests
           run: ctest --test-dir build/msvc --output-on-failure
   ```
   - The cache key and the clone line are the same as in `wheels.yml`, so the two workflows share one cached Embree source.
   - Do not add a third-party action to set up MSVC. `vswhere.exe` and `vcvars64.bat` ship with the runner image.
   - The `linux` job is unchanged.

Do not change any other file. In particular, `wheels.yml`, `third_party/` and `pyproject.toml` stay as they are.
