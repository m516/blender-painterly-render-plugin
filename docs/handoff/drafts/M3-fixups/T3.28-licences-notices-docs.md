# T3.28 — Licences, notices, docs and the wheels path filter (M3 review panel #3, #4, #8, #13–#16)
Milestone: M3 · Depends on: T3.27 (and, before it, T3.22 and T3.23, which also edit `docs/architecture.md` and `THIRD_PARTY_NOTICES.md`) · Parallel-safe: no

## Goal
This card closes seven confirmed findings of the M3 review panel. They are all about licences, notices, docs and CI triggers.
No compiled code changes, and neither do rendered output, the oracle or the exports.

- **Panel #3: tsl::robin_map.** nanobind 3.1.0 compiles tsl::robin_map (MIT, Copyright (c) 2017 Thibaut
  Goetghebuer-Planchon) into its static library: `src/nb_internals.h:15` includes `<tsl/robin_map.h>`, and
  `cmake/nanobind-config.cmake:297-309` links `tsl::robin_map`. `src/blender/CMakeLists.txt` builds that library with
  `NB_STATIC`, so the code ends up in `_painterly`. `strings` on the module finds "The hash table exceeds its maximum size.",
  which only `tsl/robin_growth_policy.h` contains. nanobind's wheel ships the robin_map headers without a LICENSE file, and
  nanobind's own BSD text does not cover it. New: `LICENSES/MIT-robin-map.txt`, made from `robin_map.h` lines 2-22 with the
  comment markers removed, plus a notices row.
- **Panel #13 (and Syrah, from its first confirming vote): Embree's third-party programs.** The Embree row says the
  `third-party-programs*.txt` files "cover TBB, OIDN and DPC++, components we do not build". That sentence is wrong twice:
  - SSE2NEON is entry 5.4 of Embree v4.4.1's `third-party-programs.txt` (line 700). Arm64 builds compile Embree's own copy,
    `common/simd/arm/sse2neon.h`, which `emulation.h:12` and `avx2neon.h:7` include.
  - Syrah is entry 8.1 (line 844), under a customized BSD 3-clause licence. `common/math/transcendental.h:5-7` says its
    `fastapprox` functions come from ispc, mostly from Syrah. `kernels/common/default.h:21` includes that header, and the
    instance code calls `fastapprox` through `slerp` (`common/math/quaternion.h:247-249`, called from
    `kernels/common/scene_instance.cpp:302`). We build instance geometry, so the code is in every build. Syrah's licence
    requires binary redistributions to reproduce its notice.

  A grep of Embree's `common/`, `kernels/` and `include/` finds no other third-party code: no Gruenschloss, PCG, stb,
  ImGui, GLFW, OpenEXR, TinyEXR, Catch2, OpenSubdiv or blue-noise code. TBB appears only in CMake files and in
  `taskschedulertbb.h`, which INTERNAL tasking does not compile. New: `LICENSES/BSD-3-Clause-syrah.txt`, Embree's entry 8.1
  verbatim. The sentence is rewritten.
- **Panel #14: Cycles names its text.** Every other statically linked component names its full licence text. The Cycles
  row names none, although `LICENSES/Apache-2.0.txt` (T0.1, "covers Cycles and Embree") ships in the wheel.
- **Panel #16: the doubled "exports:".** `_render_text` prints `<check name>: <rule>`, so the PE rule string, which itself
  starts with `exports:`, renders as `[PASS] exports: exports: PyInit__painterly ...`. The ELF and Mach-O rules have no such
  prefix. (Card T2.9 gave the rendered line as the rule string, and its implementer copied it literally.) A new test pins
  the rendered line.
- **Panels #8 and #15 (decision D38): exports per OS.** `docs/architecture.md`, "Isolation inside Blender", still says that
  `_painterly` exports exactly one symbol. Since T2.9, the Windows rule deliberately allows the members of nanobind's two
  `NB_EXPORT` exception classes (19 exports in CI run 37935120179). D38 says: "architecture.md and plan.md state the per-OS
  rule: on Windows `_painterly` also exports the members of nanobind's two NB_EXPORT exception classes (T2.9)". Opus already
  fixed `docs/plan.md:89` and `:254` (commit `696dc0c`). This card fixes `docs/architecture.md`, and the two comments in
  `src/blender/CMakeLists.txt` that make the same claim. Line 27 there ("Windows: nanobind already exports only PyInit") is
  false since T2.9.
- **Panel #4 (decision D39 withdrew T3.29 and moved this finding here): the wheels path filter.** Since T3.2/T3.3,
  `third_party/cycles` sources are compiled into the module. `tools/symbol_audit.py` runs in the cibuildwheel test-command
  (`pyproject.toml`) and in the repaired-wheel step of `wheels.yml`. Yet `on.pull_request.paths` covers neither, nor
  `wheels.yml` itself. So a PR that changes only a vendored file, the audit rules or the workflow builds and audits no wheel.
  Three paths are added. D39: macOS is low priority, and there is no macOS CI test job (panel #2 is not taken up).
