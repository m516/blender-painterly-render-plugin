# T3.27 — `tools/vendor_sync.py` reads upstream files from the pinned commit's git objects, never from a checkout's working tree (M3 panel #0)
Milestone: M3 · Depends on: T3.1, T3.26 · Parallel-safe: no

## Goal
This card fixes finding #0 of the M3 review panel (major; two independent reproductions confirmed it). It is Python
only: `tools/vendor_sync.py` and its test file `tests/core/test_vendored.py`. No C++, CMake or oracle source changes, and
nothing under `third_party/` changes. Never run `make oracle`.

**The defect.** T3.1's tool promises pinned, hash-checked vendoring. It reads every upstream file from the checkout's
working tree instead: `_derive` calls `source.read_bytes()` on `<checkout>/<root>/<upstream_path>`
(`tools/vendor_sync.py:412-421` at `696dc0c`). `ensure_checkout` (`:339-347`) checks only that the checkout's HEAD is the
pinned commit. Nothing compares the working tree with that commit. The panel reproduced two consequences on scratch
copies:
1. **A locally edited checkout file gets vendored silently.** The panel appended `/* tampered */` to
   `.cache/vendor/blender-v5.2.2/intern/cycles/util/hash.h` and ran `sync`. It exited 0, and in `VENDORED.toml` both
   `upstream_sha256` and `sha256` of `util/hash.h` changed from `9177a2ba…` to `7d3d24c1…`. After that, `check --upstream`
   passed ("64 vendored files match …"), so the corruption could no longer be detected.
   - `add` has the same defect, and M6a vendors about 149 more files with it.
   - So does `closure`, which decides which files `add` gets.
2. **End-of-line conversion at checkout.** Under `core.autocrlf=true`, the Git for Windows default, git writes the Cycles
   sources with CRLF, because Blender v5.2.2's `.gitattributes` sets no `eol` or `text` rule for them.
   - `check --upstream` then fails with `util/hash.h: upstream sha256 2fa769e7… differs from VENDORED.toml 9177a2ba…`.
   - `sync` would rewrite every vendored file and every hash.
   - The pinned commit's git object still holds the LF bytes.

**After this card**, every upstream byte and every upstream file list comes from the pinned commit's git objects, read
from the checkout's own repository:
- file bytes come from `git --git-dir <checkout>/.git cat-file blob <commit>:<root>/<path>` (new `upstream_blob`);
- file lists come from `git --git-dir <checkout>/.git ls-tree -r -z <commit>:<root>` (new `upstream_files`);
- the root check is `git cat-file -t <commit>:<root>`, which must print `tree`.

`sync`, `add`, `remove` (which ends in a sync), `check --upstream` and `closure` all use these. `fetch` is unchanged, and
`check` without `--upstream` still never touches a checkout. In a checkout, `<checkout>` is always the repository top
(`checkout_dir(upstream)`), never `<checkout>/<root>`.

**No dirty-tree check is needed.** After this card no subcommand reads a checkout's working tree, so nothing in it can
reach `third_party/`: not edited, deleted or untracked files, and not CRLF conversion. Its state is therefore not
checked. A `git status` check would not be enough anyway, because with `core.autocrlf=true` git reports the converted
files as unmodified. The existing refusal of a checkout whose HEAD is not the pinned commit stays as it is
(`ensure_checkout`), and it now has tests for `sync`, `check --upstream`, `add` and `closure`.

**Nothing vendored changes.** Opus checked the real checkouts at `696dc0c`: all 64 pinned blobs hash to their recorded
`upstream_sha256`. So `sync` reproduces `third_party/cycles/` and `VENDORED.toml` byte for byte, and `closure` prints
byte-identical output (A4). The CLI, its options and its exit statuses stay the same. Two error messages change (see
Interface).

**Tests.** `tests/core/test_vendored.py` keeps its offline `check` test and gains seven test functions, ten test cases
in all. They run on a fixture upstream: a git repository that each test commits under `tmp_path`, so they need neither
the network nor `.cache/vendor`. The tests check that:
- a checkout file that was edited, or one that was deleted, changes nothing, because the pinned blob is used;
- CRLF conversion at checkout changes nothing;
- `check --upstream` detects a vendored file whose bytes and hashes match an edited working tree but not the pinned blob.
  Panel #0's `sync` left exactly this state behind;
- `add` refuses a file that exists only in the working tree;
- `closure` ignores an `#include` line that was added in the working tree;
- `sync`, `check --upstream`, `add` and `closure` all refuse a checkout that is off its pin;
- object paths resolve both under a root and with the root at the repository top.

```python
def _object_spec(upstream: Upstream, path: str = "") -> str:
    """The git revision `<commit>:<repository path>` of a root-relative path in the pinned commit.

    The empty path names the upstream root itself: `<commit>:intern/cycles` for cycles, and the
    commit's top tree `<commit>:` when the root is the repository root.
    """
    in_repository = "/".join(part for part in (upstream.root, path) if part)
    return f"{upstream.commit}:{in_repository}"


def _object_type(checkout: Path, spec: str) -> str | None:
    """Type ("blob", "tree", ...) of the object that the revision spec names, or None if none.

    Only the object store of the checkout's own repository (its .git) is read.
    """
    try:
        return _git(["--git-dir", str(checkout / ".git"), "cat-file", "-t", spec])
    except VendorError:
        return None


def _missing_file(upstream: Upstream, path: str) -> VendorError:
    """The error for a root-relative path that is not a file in upstream's pinned commit."""
    return VendorError(f"{path} is not a file in upstream {upstream.name} at {upstream.commit}")


def upstream_files(upstream: Upstream, checkout: Path) -> frozenset[str]:
    """Root-relative paths of every file under upstream's root in its pinned commit.

    The list comes from the commit's tree objects (`git ls-tree -r`), not from the working tree,
    so an untracked or deleted working-tree file changes nothing. Directories are not listed.
    """
    listing = _git_bytes(
        ["--git-dir", str(checkout / ".git"), "ls-tree", "-r", "-z", _object_spec(upstream)]
    )
    files: set[str] = set()
    for record in listing.split(b"\0"):
        if not record:
            continue
        # One record per entry: "<mode> <type> <object id>\t<path>" (git ls-tree -z).
        info, _, name = record.partition(b"\t")
        if info.split(b" ")[1] == b"blob":
            files.add(name.decode("utf-8"))
    return frozenset(files)


def upstream_blob(upstream: Upstream, checkout: Path, path: str) -> bytes:
    """Bytes of the root-relative path in upstream's pinned commit, from the checkout's git objects.

    `git cat-file blob` prints the stored object unchanged: no working-tree file is read, and no
    end-of-line conversion or other checkout filter applies. Raises VendorError when the pinned
    commit has no file at path.
    """
    spec = _object_spec(upstream, path)
    if _object_type(checkout, spec) != "blob":
        raise _missing_file(upstream, path)
    return _git_bytes(["--git-dir", str(checkout / ".git"), "cat-file", "blob", spec])
```
