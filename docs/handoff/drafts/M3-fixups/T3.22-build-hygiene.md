# T3.22 — Build hygiene: warnings on our own targets only, header-only doctest, plain target names, `painterly_kernel`, one audit run (TQ.1 F9–F11, F13, F15)
Milestone: M3 · Depends on: T3.12, TQ.1, T3.19, T3.20, T3.21 · Parallel-safe: no

## Goal
This card implements the audit's proposed card TQ.1-2 (`docs/audits/TQ.1.md`), except F12. Decision D34 moved F12 (the
selftest through `painterly_bvh`) to T3.15. The card also takes in four confirmed findings of the M3 review panel: #5, #6, #9
and #18. Afterwards, the project's own targets compile with warnings on, every third-party include directory is SYSTEM, and
a build prints no warning at all.

- **F9 and panel #6: warnings on our own targets only.** No target enabled warnings, so nothing stopped new ones from
  accumulating. A new module, `cmake/painterly_warnings.cmake`, defines `painterly_target_warnings(<target>)`. It adds
  `-Wall -Wextra -Wshadow`, or `/W4` on MSVC, as PRIVATE options of five targets: `painterly_util`, `painterly_bvh`,
  `painterly_integrator`, `painterly_tests` and `_painterly`. It is never called for `cycles_*`, doctest, Embree, nanobind or
  the oracle.
  - `-Wshadow` is the flag the panel asked for. Vendored Cycles and our code share `namespace painterly`, and vendored
    `util/simd.h:67-126` defines the namespace-scope variables `True`, `False`, `zero`, `one`, `neg_inf`, `inf`, `pos_inf` and
    `step`. A local of the same name hides the global without any message.
  - Measured at `696dc0c` with GCC 13: compiling our 19 translation units with these flags, and with the vendored directories
    as plain `-I`, produced 652 `-Wshadow` reports inside vendored Cycles headers and 41 inside nanobind's headers, counted
    once per translation unit. Our own code had five distinct reports: three `-Wshadow` in `src/painterly`, and one
    `-Wshadow` and one `-Wunused-parameter` in `src/test`. T3.19 and T3.20 add none.
  - So every third-party include directory becomes SYSTEM, and compilers report nothing from SYSTEM headers:
    - `third_party/cycles` and `third_party/cycles/sse2neon` (in `src/cycles/CMakeLists.txt`);
    - Embree's include directory, through `painterly_embree` and the `SYSTEM` property of Embree's `embree` target;
    - doctest, through the new `painterly_doctest`;
    - nanobind and Python, through nanobind's own `NB_SUPPRESS_WARNINGS` option.

    A SYSTEM directory is searched after the plain ones. Our TUs then have exactly two plain include directories,
    `src/cycles/shim` and `src`, so they search `src/cycles/shim`, `src`, `third_party/cycles`, `third_party/cycles/sse2neon`.
    The declared order (D1, `docs/architecture.md`) does not change. No path exists under both `src/` and
    `third_party/cycles/`, because their top-level directories are disjoint, so every include still resolves to the same
    file. A new test in `tests/core/test_shims.py` keeps them disjoint.
  - Our own hits are fixed by renames. Each is bitwise neutral:
    - `src/painterly/kernel/integrator/path.h`: the local `zero` of `painterly_trace_pixel` becomes `black`. It shadows
      `util/simd.h:90`.
    - `PainterlyRenderBuffers::reset(width, height)`: the parameters become `new_width` and `new_height`. They shadow the
      members.
    - `src/test/test_analytic.cpp:376`: the local `zero` becomes `zero_direction`. This is the fourth hit, which a panel vote
      found.
  - The `-Wunused-parameter` report is in the verbatim smallpaint copy in `test_analytic.cpp` (Plane's `normal`,
    `smallpaint_painterly.cpp:91`). It is silenced for that file only, and the copy stays byte-identical.
- **F10 and panel #9: doctest header-only.** With CMake 3.28, the declared minimum, every configure printed two doctest
  warnings: a `CMake Deprecation Warning` and a CMP0063 `CMake Warning (dev)`. The venv's CMake 4.4.4, which `make` uses,
  prints neither. That is why this card's probe configures with `/usr/bin/cmake` 3.28.3. doctest is now fetched with a
  `SOURCE_SUBDIR` that does not exist, so its CMakeLists.txt never runs. The INTERFACE target `painterly_doctest` (SYSTEM)
  replaces `doctest::doctest`, and `CMAKE_POLICY_VERSION_MINIMUM` is no longer needed.
- **F11: one target-naming convention.** Every target of this project has a plain name and no namespaced alias. The alias
  `painterly::embree` is removed, and consumers link `painterly_embree`. That is already the name of our private Embree
  everywhere else: the CMake module, `EMBREE_API_NAMESPACE` and `EMBREE_LIBRARY_NAME`.
- **F13: `painterly_kernel`.** The header-only kernel gets an INTERFACE target that links `painterly_bvh` and `cycles_util`.
  `painterly_integrator` links it instead of `painterly_bvh`, and `painterly_tests` links it too.
- **F15: one run of each audit.** `make check` ran the symbol audit twice, through pytest's `tests/core/test_symbol_audit.py`
  and then `make audit`, and it ran the vendor check twice in the same way. `check` becomes `lint build test`. The pytest
  wrappers stay, because CI's `make test` relies on them, and `make audit` and `make vendor-check` stay as standalone targets.
- **Panel #5: explicit ustring constructors.** The shim `ustring` (`src/cycles/shim/util/param.h`) had implicit
  `ustring(const char *)` and `ustring(std::string_view)` constructors. OpenImageIO v3.1.13.1's are `explicit`
  (`ustring.h:143, :151`), and Blender v5.2.2 pins that version (`build_files/build_environment/cmake/versions.cmake:298`).
  - With implicit constructors, code compiled here that does not compile upstream. Every `u == "literal"` also interned the
    literal under the global mutex, and GCC 14 (the manylinux wheel build) warned at `graph/node.h:213` because of them.
  - Upstream compares ustrings with C strings (`scene/shader_graph.cpp:96, :107`, which M6a vendors). The constructors
    become `explicit`, so the shim gains OpenImageIO's two lexicographic `operator==` overloads, for `std::string_view` and
    `const char *` (`ustring.h:578, :581`). C++20 derives `!=` and the reversed operand order from them.
  - A new doctest checks both properties.
- **Panel #18: Embree comments.** `cmake/painterly_embree.cmake` said that `_painterly` uses Embree through `painterly_bvh`.
  In fact `_painterly` links Embree directly, for `src/blender/selftest.cpp`. The comments now say so.

Nothing here changes rendered output. No oracle source changes, the oracle's compile flags stay the same, Embree is not
recompiled, and default renders stay byte-identical. The renames do not change any arithmetic, and every existing doctest
passes unchanged. The MSVC side (`/W4`, `/wd4100`, `/external:I`) cannot be compiled here. The orchestrator checks it on CI.

## Create
### C1. `cmake/painterly_warnings.cmake` (whole file)
```cmake
# SPDX-License-Identifier: GPL-3.0-or-later
#
# Compiler warnings for the project's own targets (TQ.1 F9, M3 review panel #6).
#
# painterly_target_warnings(<target>) adds the warning flags to the target's own sources. They are PRIVATE, so they never
# reach a consumer. The callers are painterly_util, painterly_bvh, painterly_integrator, painterly_tests and _painterly,
# and every later painterly_* library calls it too. The vendored Cycles libraries (cycles_*), Embree, doctest, nanobind
# and the oracle (smallpaint_oracle) never call it. Their headers reach our sources through SYSTEM include directories,
# and compilers report no warning from those, so the flags report our code only.
#
# -Wshadow: vendored Cycles and our code share namespace painterly (docs/architecture.md, "Source layout and naming"), so
# a local named like a vendored namespace-scope variable (True, False, zero, one, neg_inf, inf, pos_inf, step;
# util/simd.h:67-126) silently hides it. MSVC: /W4 is the counterpart of -Wall -Wextra, and its level 4 includes the
# declaration-hides warnings C4456-C4459.
function(painterly_target_warnings target)
  if(MSVC)
    target_compile_options(${target} PRIVATE /W4)
  else()
    target_compile_options(${target} PRIVATE -Wall -Wextra -Wshadow)
  endif()
endfunction()
```

        if our_flags & set(words):
            problems.append(f"{name}: has {sorted(our_flags & set(words))}")
