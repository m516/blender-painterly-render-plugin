# T8.1 — Release workflow: three wheels, per-platform extension zips, GPL source tarball, GitHub Release, dry run
Milestone: M8 · Depends on: M4–M7 (T4.4 `tools/build_extension.py` and `tests/blender_it/run_reference.py`; T7.1–T7.4), T2.9 · Parallel-safe: no

## Goal
After this card:
- Pushing a tag `v<version>` runs `.github/workflows/release.yml`:
  1. `plan` classifies the tag and checks that the three version sources agree;
  2. `wheels` calls `.github/workflows/wheels.yml` (`workflow_call`), which builds, audits and coexistence-tests the three
     cp312-abi3 wheels exactly as on a pull request;
  3. `package` runs `tools/release.py package`, which packs the wheels into one extension zip per platform with
     `blender --command extension build --split-platforms`, writes `painterly-<version>-source.tar.gz` (the exact tracked
     tree of the tagged commit, `third_party/` and `LICENSES/` included) and `SHA256SUMS`, and verifies every byte of them;
  4. `install` installs each zip into Blender 5.2.2 on Linux and Windows and renders the built-in reference scene through
     it. macOS has no `install` leg: D39 allows no macOS CI test job, and the macOS zip is still built and byte-verified
     in `package`;
  5. `publish` creates the GitHub Release `v<version>` with exactly those five assets.
- A tag `v<version>-dryrun.<n>`, or a manual dispatch, runs jobs 1–4 and skips `publish`. Its assets stay available as the
  workflow artifact `release`.
- Any other tag, or disagreeing version sources, fails `plan` within seconds, before a wheel is built.
- `tools/build_extension.py` (T4.4) builds the split zips from any number of wheels through one function, and every zip it
  builds, including `make extension`'s, carries `LICENSE`, `THIRD_PARTY_NOTICES.md` and `LICENSES/`. Its command line and its
  outputs for `make extension` (`dist/<zip>`, the one-line `build/extension/zip_path.txt`) are unchanged.

  1. With `--split-platforms` and `--output-dir D`, Blender writes `D/<id>-<version>-<platform with "-" → "_">.zip`, e.g.
     `painterly-0.1.0-linux_x64.zip`, `painterly-0.1.0-macos_arm64.zip`, `painterly-0.1.0-windows_x64.zip`. It prints
     `created: "<path>"` for the **last** zip only, so never parse that line.
  2. Each zip's `blender_manifest.toml` is the staged manifest, byte for byte, followed by a generated table:
     ```
     # BEGIN GENERATED CONTENT.
     # This must not be included in source manifests.
     [build.generated]
     platforms = ["linux-x64"]
     wheels = ["./wheels/painterly_core-0.1.0-cp312-abi3-manylinux_2_27_x86_64.manylinux_2_28_x86_64.whl"]
     # END GENERATED CONTENT.
     ```
     The top-level `platforms` and `wheels` keep all three entries. Blender reads `[build.generated]` in their place.
  3. Every file under the source directory that the manifest does not list, and that `paths_exclude_pattern` does not
     exclude, is packed into **every** zip. A stale wheel left in `wheels/` by an earlier run ends up in all three zips.
  4. A listed wheel that is missing fails the build with exit 1, after the zips of the platforms before it were written.
  5. `extension validate <zip>` exits 1 on an invalid manifest, but exits 0 for a zip that lacks its listed wheel. The
     wheel check is therefore ours.
  6. `extension install-file -r user_default -e <zip>` exits 0 even when it refuses a zip built for another platform
     (`ERROR painterly: This platform (linux-x64) isn't one of (windows-x64)`). The exit status proves nothing; the
     registration assert in `run_reference.py` decides.
  7. `git archive --format=tar.gz --prefix=P/ HEAD` stores the commit id as the global pax header `comment`, a directory
     member `P`, and file modes 0664 and 0775 (git's default `tar.umask` 0002). For every regular file, the SHA-1 of
     `b"blob %d\0" % len(data) + data` equals the blob id that `git ls-tree -r HEAD` prints (the repository's object format
     is `sha1`).
  8. PyYAML (YAML 1.1) loads a workflow's `on:` key as the boolean `True`: read `wf[True]`, never `wf["on"]`.

## Interface

### Tags and modes
| Event | `release.py plan` prints | Jobs that run |
|---|---|---|
| push of tag `v<version>` | `mode=release` | `plan`, `wheels`, `package`, `install`, `publish` (creates Release `v<version>`) |
| push of tag `v<version>-dryrun.<n>` (`<n>` decimal digits) | `mode=dry-run` | all but `publish` |
| `workflow_dispatch` on any ref | `mode=dry-run` | all but `publish` |
| any other tag, e.g. `v<other version>`, `v<version>-rc.1`, `vendor-x` | nothing on stdout, exit 1 | `plan` fails; nothing else runs |

`<version>` is the one value shared by the three **version sources**, in this order:
`src/blender/addon/blender_manifest.toml` (`version`), `pyproject.toml` (`[project] version`) and `CMakeLists.txt`
(`project(painterly VERSION X.Y.Z …)`). Releasing X.Y.Z means one commit that sets X.Y.Z in all three, an optional dry run
with tag `vX.Y.Z-dryrun.1`, then tag `vX.Y.Z`.

### Release assets (exact names; `painterly` is the manifest `id`)
| Asset | Content |
|---|---|
| `painterly-<version>-linux_x64.zip` | the extension with exactly the manylinux x86_64 wheel; `[build.generated] platforms = ["linux-x64"]` |
| `painterly-<version>-macos_arm64.zip` | the extension with exactly the macOS arm64 wheel; `platforms = ["macos-arm64"]` |
| `painterly-<version>-windows_x64.zip` | the extension with exactly the win_amd64 wheel; `platforms = ["windows-x64"]` |
| `painterly-<version>-source.tar.gz` | `git archive` of the tagged commit, prefix `painterly-<version>/`: every tracked file, byte for byte |
| `SHA256SUMS` | one line `<64 lowercase hex>  <name>\n` (two spaces) per asset above, sorted by name: the `sha256sum -c` format |

- Download URL: `https://github.com/m516/blender-painterly-render-plugin/releases/download/v<version>/<asset>`, in general
  `https://github.com/${GITHUB_REPOSITORY}/releases/download/<tag>/<asset>`.
- Every extension zip holds, at its root, the add-on files of `src/blender/addon/` (minus the manifest's
  `paths_exclude_pattern`), `blender_manifest.toml`, `wheels/<one wheel>`, `LICENSE`, `THIRD_PARTY_NOTICES.md` and
  `LICENSES/<every file of LICENSES/>`.
- Workflow artifact `release`, uploaded in every mode: `release/<the five assets>` and `release-notes.md`.

### `tools/release.py` command line
```
python -I tools/release.py plan (--tag TAG | --dispatch)
    stdout: exactly "mode=<release|dry-run>\nversion=<X.Y.Z>\n" (the format of $GITHUB_OUTPUT); exit 0.
    On any failure: nothing on stdout, "release: <reason>" on stderr, exit 1.
python -I tools/release.py zip-name --platform {linux-x64,macos-arm64,windows-x64}
    stdout: "<extension zip name of that platform>\n"; reads no git state.
python -I tools/release.py package --blender PATH --wheel-dir DIR
        [--out-dir dist/release] [--notes dist/release-notes.md] [--work-dir build/release]
    Builds and verifies the five assets into --out-dir, which must not exist yet; writes the release notes to --notes;
    stages under <work-dir>/extension/<id>. stdout: the path of each asset, one per line, in asset_names() order.
    --work-dir must not be `build`: the release stages into <work-dir>/extension/<id>, and `build` would stage into
    `build/extension/painterly`, the directory `make extension` stages into (T4.4) and empties (Step 2). The default
    `build/release` is chosen for that reason.
```

### 2. `tools/build_extension.py`
Keep T4.4's command line, its `make wheel` fallback, its add-on copy mechanism and every helper it already has. Add or
rename to the functions of "Interface":
- `parse_wheel_filename(name)`: PEP 427, `{distribution}-{version}(-{build tag})?-{python tag}-{abi tag}-{platform tag}.whl`.
  Strip the `.whl` suffix (a name without it raises `ValueError`), split on `-`: 5 parts have no build tag, 6 parts have
  one, any other count raises `ValueError` naming the file.
- `blender_platform_from_wheel(wheel)`, from this table (module constant `WHEEL_PLATFORM_TAGS`):
  ```python
  # Blender platform of each element of a PEP 425 platform tag set. Blender's own, wider rule is
  # blender_platforms_from_wheel_platform() in scripts/addons_core/bl_pkg/cli/blender_ext.py (v5.2.2). This table admits only
  # the three v1 platforms (docs/plan.md, Owner decisions: Platforms) and the tags our wheels carry: linux_x86_64 from a
  # local `uv build` (T2.4), manylinux_X_Y_x86_64 and the PEP 600 legacy aliases from auditwheel, macosx_X_Y_arm64 (T2.4:
  # deployment target 11.0) and win_amd64.
  WHEEL_PLATFORM_TAGS = (
      (re.compile(r"linux_x86_64|manylinux_[0-9]+_[0-9]+_x86_64|manylinux(?:1|2010|2014)_x86_64"), "linux-x64"),
      (re.compile(r"macosx_[0-9]+_[0-9]+_arm64"), "macos-arm64"),
      (re.compile(r"win_amd64"), "windows-x64"),
  )
  ```
  Split the platform tag on `.`. Each element must `fullmatch` exactly one pattern, and all elements must give the same
  platform; otherwise raise `ValueError` naming the wheel and the element. Replace T4.4's own derivation with this function.
- `extension_zip_name(extension_id, version, platform)` returns `f"{extension_id}-{version}-{platform.replace('-', '_')}.zip"`.
  Comment it as Blender's naming under `--split-platforms` (`blender_ext.py` v5.2.2, `subcmd_author.build`).
- `stage_extension(wheels, staging_dir, *, addon_dir, root)`:
  1. No wheels raises `ValueError`. Two wheels with the same platform raise `ValueError` naming both files.
  2. If `staging_dir` exists, `shutil.rmtree(staging_dir)`. Comment why: Blender packs every unlisted file under the source
     directory into every zip ("Read first", fact 3), so a stale wheel would ship in all of them.
  3. Copy `addon_dir` to `staging_dir` with T4.4's mechanism.
  4. Licence texts: for each name in `LICENCE_FILES`, and for `LICENCE_DIR/<f>` for every regular file `f` of
     `root / LICENCE_DIR` (sorted), raise `FileExistsError` if the staged path already exists (the add-on is never
     overwritten), then `shutil.copyfile` it from `root`. Comment why: the zip carries the add-on's own GPL licence, and the
     Apache-2.0 texts that `get_panels()` (copied from Cycles, T4.2) and the statically linked Embree require. The rule:
     every regular file of `LICENSES/` is staged (the SPDX spelling; only the constant names keep the British `LICENCE_`
     spelling), while `LICENCE_FILES` names the two top-level notices. A card that adds a top-level notice therefore
     changes `LICENCE_FILES`, the literal list of `verify_extension_zip` check 4, and the acceptance one-liner that names
     the two notices (T2.9 owns `LICENSES/`).
  5. Copy each wheel to `staging_dir / "wheels" / wheel.name`.
  6. Manifest. If the source manifest already has a top-level `platforms` or `wheels` key, raise `ValueError` (T4.1 leaves
     both to this tool, and a duplicate TOML key is invalid). Otherwise insert two lines immediately before the first line
     that starts with `[` (the first table header; T4.1's `[build]`), or at the end if there is none:
     `platforms = <json.dumps(platforms)>` and `wheels = <json.dumps(["./wheels/" + w.name for w in wheels in platform order])>`.
     A key after a table header would belong to that table. `json.dumps` of a list of ASCII strings is a valid TOML array.
     Then assert that `tomllib.loads` of the staged text gives exactly those two lists.
  7. Return the platforms, sorted. The wheels are listed in that same order.
- `build_extension(blender, wheels, staging_dir, output_dir, *, addon_dir, root)`: `stage_extension`, then
  `output_dir.mkdir(parents=True, exist_ok=True)`, then
  `subprocess.run([str(blender), "--command", "extension", "build", "--source-dir", str(staging_dir), "--output-dir", str(output_dir), "--split-platforms"], check=True, stdout=sys.stderr)`.
  Blender's progress lines go to stderr, so the stdout of `tools/release.py package` carries only asset paths.
  Read `id` and `version` from the staged manifest. Return
  `[output_dir / extension_zip_name(id, version, p) for p in platforms]`, after raising `FileNotFoundError` for any that is
  missing. Never parse Blender's `created:` line (fact 1).
- `main()`: T4.4's behaviour through `build_extension(blender, [wheel], <T4.4 staging dir build/extension/painterly>, <T4.4 output dir dist>)`.
  It still prints the one zip path and writes it, alone on one line, to `build/extension/zip_path.txt` (T7.2 reads it with
  `.read().strip()`). Only `main()` writes that file.
- Module docstring: describe both entry points (`main` for `make extension`, `build_extension` for `tools/release.py`).
- Standard library only. A module-level `if __name__ == "__main__":` guard, so importing it runs nothing.

### 3. `tools/release.py`
Module docstring: the usage of "Interface", the five assets, and that each check below is an exact equality.
Constants, each commented with its origin:
```python
# The tag forms of a release and of a dry run (this card). [0-9], not \d: \d also matches non-ASCII digits.
RELEASE_TAG = re.compile(r"v(?P<version>[0-9]+\.[0-9]+\.[0-9]+)")
DRY_RUN_TAG = re.compile(r"v(?P<version>[0-9]+\.[0-9]+\.[0-9]+)-dryrun\.[0-9]+")
# CMakeLists.txt's project() line; its VERSION becomes _painterly.version_info()["version"] (src/blender/CMakeLists.txt).
# The lookahead ends the match after X.Y.Z: a four-component VERSION is no match, so it raises instead of reading 0.1.0
# out of 0.1.0.1, which PAINTERLY_VERSION would then carry and engine.init() would refuse (T4.1).
CMAKE_PROJECT_VERSION = re.compile(r"^project\(painterly VERSION ([0-9]+\.[0-9]+\.[0-9]+)(?=[\s)])", re.MULTILINE)
# scikit-build-core's wheel.py-api = "cpXY" builds a stable-ABI wheel, whose ABI tag is abi3 (PEP 384, PEP 425).
STABLE_ABI_TAG = "abi3"
```
Load `tools/build_extension.py` once at import with `importlib.util.spec_from_file_location("build_extension", <tools>/build_extension.py)`.
Under `python -I` the script's directory is not on `sys.path`. Convert `ValueError` from its parsing functions into `ReleaseError`.

Functions, in order:
- `source_versions(root)`: the manifest's `version` (tomllib), pyproject's `[project] version` (tomllib), and the first
  `CMAKE_PROJECT_VERSION` match in `CMakeLists.txt`. The accepted forms are exactly those three keys, and for CMake a line
  that starts `project(painterly VERSION X.Y.Z` with single spaces and ASCII digits, followed by whitespace or `)`:
  `CMAKE_PROJECT_VERSION` matches it with or without a `LANGUAGES` suffix, and reads nothing after X.Y.Z. No match raises
  `ReleaseError("CMakeLists.txt: no 'project(painterly VERSION X.Y.Z' line")`. A missing `version` key in the manifest or
  in pyproject, and invalid TOML in either, raise `ReleaseError` naming the file, as the CMake case does: `plan` then
  prints `release: <reason>` rather than a traceback.
- `release_version(root)`: the shared value. If they differ, raise `ReleaseError` listing every source with its version, in
  `VERSION_SOURCES` order, e.g. `version sources disagree: src/blender/addon/blender_manifest.toml 0.1.0, pyproject.toml 0.1.1, CMakeLists.txt 0.1.0`.
- `classify_tag(tag, version)`: try `RELEASE_TAG` (mode `release`), then `DRY_RUN_TAG` (mode `dry-run`), with `fullmatch`.
  A match whose `version` group differs raises `ReleaseError(f"tag {tag} names version {found}, but the version sources say {version}")`.
  No match raises `ReleaseError(f"tag {tag} is neither v{version} (release) nor v{version}-dryrun.<n> (dry run)")`.
- `source_tarball_name(extension_id, version)` = `f"{extension_id}-{version}-source.tar.gz"`.
- `asset_names(extension_id, version)` = `sorted([*(extension_zip_name(id, version, p) for p in RELEASE_PLATFORMS), source_tarball_name(id, version), CHECKSUMS_NAME])`.
- `check_wheels(wheel_dir, root)`:
  - every entry of `wheel_dir` is a regular file whose name ends in `.whl`; anything else raises `ReleaseError` naming it;
  - for each wheel, `parse_wheel_filename`: `distribution == re.sub(r"[-_.]+", "_", <pyproject [project] name>).lower()`
    (the wheel-name normalization of PEP 427 and the binary distribution format spec: `painterly_core`),
    `version == release_version(root)`, `build is None`, `python == <pyproject [tool.scikit-build] wheel.py-api>`
    (tomllib nests the dotted key: `["tool"]["scikit-build"]["wheel"]["py-api"]`), `abi == STABLE_ABI_TAG`;
  - no element of the platform tag set starts with `linux_`: a release ships only auditwheel-repaired manylinux wheels,
    whose glibc baseline T2.9 enforces. This ban lives only here: `blender_platform_from_wheel` (Step 2) is a total mapping
    over the tags it knows, and admits `linux_x86_64` for a local `uv build` (T2.4);
  - the platforms (`blender_platform_from_wheel`) are distinct and their set equals `set(RELEASE_PLATFORMS)`. Otherwise
    raise `ReleaseError` naming the duplicates, the missing and the extra platforms;
  - return `{p: wheel}` in `RELEASE_PLATFORMS` order.
- `git_tree(root, rev)`: `git -C <root> rev-parse --show-object-format` must print `sha1` (the object format that
  `git_blob_id` defines); otherwise raise
  `ReleaseError(f"{root}: the repository's object format is {found}, not sha1: git_blob_id defines sha1")`, with `found`
  stripped. Parse `git -C <root> ls-tree -r -z --full-tree <rev>`: each NUL-ended
  record is `<mode> <type> <oid>\t<path>`. A type other than `blob` (a `commit` is a submodule, which `git archive` omits)
  raises `ReleaseError`.
- `git_blob_id(data)` = `hashlib.sha1(b"blob %d\0" % len(data) + data).hexdigest()`. Comment it as git's object id of a blob
  (git-hash-object(1), object format sha1), not as a checksum choice.
- `write_source_tarball(root, out_dir)`:
  `git -C <root> archive --format=tar.gz --prefix=<id>-<version>/ -o <absolute path> HEAD`, where the path is
  `out_dir / source_tarball_name(id, version)` resolved to an absolute path (`git -C` would resolve a relative `-o`
  against `root`). Returns that path.
- `verify_source_tarball(tarball, root)`, with `prefix = f"{id}-{version}/"`, raising `ReleaseError` on the first failing check:
  1. `tarfile.open(tarball, "r:gz").pax_headers.get("comment")` equals `git -C <root> rev-parse HEAD` (fact 7). The
     message on a mismatch is `f"{tarball.name}: archived from commit {found}, not from HEAD {head}"`;
  2. every member is the directory `prefix.rstrip("/")` or is named `prefix + <path>`;
  3. skip directory members. A regular file gives `(<"100755" if member.mode & 0o100 else "100644">, git_blob_id(<bytes>))`;
     a symlink gives `("120000", git_blob_id(member.linkname.encode()))`; any other member type raises;
  4. that mapping equals `git_tree(root, "HEAD")`. A mismatch names every missing, extra and changed path, sorted;
  5. it contains `LICENSE` and `THIRD_PARTY_NOTICES.md`, at least one path under `LICENSES/` and one under `third_party/`.
  A later card that adds an `export-ignore` or `export-subst` attribute fails check 4 by design: the tarball is the exact
  tree.
- `verify_extension_zip(zip_path, platform, wheels, root, blender)`, raising `ReleaseError` that names the zip and the member:
  1. `zipfile.ZipFile(zip_path).testzip()` is `None` (every CRC matches). Ignore names that end in `/`.
  2. Manifest. Parse the member `blender_manifest.toml` with tomllib, and the source manifest with `read_manifest(root)`.
     - Its keys are exactly `set(source) | {"platforms", "wheels", "build"}`. `build` is listed because Blender appends
       `[build.generated]` even when the source has no `[build]` table.
     - Every source key except `build` has an equal value.
     - `platforms == list(RELEASE_PLATFORMS)`, and `wheels == ["./wheels/" + wheels[p].name for p in RELEASE_PLATFORMS]`.
     - `build == {**source.get("build", {}), "generated": {"platforms": [platform], "wheels": ["./wheels/" + wheels[platform].name]}}` (fact 2).
  3. The members under `wheels/` are exactly `["wheels/" + wheels[platform].name]`, and its bytes equal that wheel file's.
  4. Licence members: `LICENSE`, `THIRD_PARTY_NOTICES.md` and `LICENSES/<f>` for every regular file `f` of `root/LICENSES`
     are all present, each byte-equal to `root/<member>`.
  5. Every other member is a regular file `root/src/blender/addon/<member>` with equal bytes. `__init__.py` is present.
     This is a subset check: Blender's `paths_exclude_pattern` may leave add-on files out, never put foreign ones in.
  6. `[str(blender), "--command", "extension", "validate", str(zip_path)]` exits 0. Otherwise raise with its output.
     A zip without its wheel validates (fact 5), which is why checks 3–5 exist.
- `write_sha256sums(out_dir)`: hash every regular file of `out_dir` except `CHECKSUMS_NAME`, sorted by name. Write
  `f"{hashlib.sha256(data).hexdigest()}  {name}\n"` per file (two spaces), as UTF-8 bytes with `\n` line ends.
  Return the path.
- `write_notes(notes, out_dir, root)`: `notes.parent.mkdir(parents=True, exist_ok=True)`, then write this text. The rows
  are read back from `SHA256SUMS`, in its order, so the notes and the checksums cannot disagree. The byte counts come from
  `stat().st_size`, `<licence>` is the manifest `license` list with each `SPDX:` prefix removed, joined with `", "`, and
  `<commit>` is `git rev-parse HEAD`:
  ```
  Painterly <version> for Blender <manifest blender_version_min> or later, built from commit <commit>.

  Download the zip for your platform and install it with **Install from Disk** in Blender's Get Extensions preferences.

  | Asset | Bytes | SHA-256 |
  |---|---|---|
  | `<name>` | <bytes> | `<sha256>` |
  …one row per SHA256SUMS line…

  `<source tarball name>` is the source of this release: the exact tracked tree of commit <commit>, including
  `third_party/` and `LICENSES/`. Painterly is licensed <licence>. `THIRD_PARTY_NOTICES.md` lists the licences of the code
  it includes, and the build fetches Embree and nanobind at the versions pinned in `cmake/painterly_embree.cmake` and
  `pyproject.toml`.
  ```
- `package(root, blender, wheel_dir, out_dir, notes, work_dir)`:
  1. `version = release_version(root)`, `id = read_manifest(root)["id"]`, `wheels = check_wheels(wheel_dir, root)`. This
     happens before anything is written, so a bad wheel set never runs Blender.
  2. `blender` must be an existing file, and `out_dir` must not exist. An existing `out_dir` raises
     `ReleaseError(f"{out_dir} exists; remove it first: a release never mixes the assets of two runs")`.
     Then `out_dir.mkdir(parents=True)`.
  3. `zips = build_extension.build_extension(blender, [wheels[p] for p in RELEASE_PLATFORMS], work_dir / "extension" / id, out_dir, addon_dir=root / "src" / "blender" / "addon", root=root)`.
     `zips` must equal `[out_dir / extension_zip_name(id, version, p) for p in RELEASE_PLATFORMS]`.
  4. `verify_extension_zip` for each platform. Then the sets of member names outside `wheels/` are equal across the three
     zips.
  5. `write_source_tarball`, then `verify_source_tarball`.
  6. `write_sha256sums(out_dir)`.
  7. `sorted(p.name for p in out_dir.iterdir()) == asset_names(id, version)`; otherwise raise naming the difference.
  8. `write_notes(notes, out_dir, root)`. Return `[out_dir / n for n in asset_names(id, version)]`.
- `main(argv)`: argparse subcommands `plan` (mutually exclusive, required `--tag TAG` | `--dispatch`), `zip-name`
  (`--platform`, choices `RELEASE_PLATFORMS`) and `package` (`--blender`, `--wheel-dir` required; `--out-dir`, `--notes`,
  `--work-dir` with the defaults of "Interface", relative to the working directory). `plan` writes nothing to stdout until both
  lines are known, so a failure leaves `$GITHUB_OUTPUT` untouched. A `ReleaseError` prints `release: <message>` to stderr and
  returns 1. `if __name__ == "__main__": sys.exit(main())`.

### 4. `.github/workflows/release.yml`, exactly
```yaml
# Release (T8.1). A tag v<version> builds the three wheels (wheels.yml, with its coexistence runs), packs one extension zip
# per platform with `blender --command extension build --split-platforms`, writes the GPL source tarball, installs and
# renders each zip in Blender on Linux and Windows, and publishes the assets as a GitHub Release. A tag v<version>-dryrun.<n>, or a
# manual dispatch, runs every job except publish. tools/release.py decides the mode and builds and verifies every asset.
name: Release

on:
  push:
    tags: ["v*"]
  workflow_dispatch:

permissions:
  contents: read

concurrency:
  group: release-${{ github.ref }}
  cancel-in-progress: false

env:
  BLENDER_VERSION: "5.2.2"

jobs:
  # Fails within seconds on a tag that is neither v<version> nor v<version>-dryrun.<n>, or when the three version sources
  # disagree, before any wheel is built.
  plan:
    runs-on: ubuntu-24.04
    outputs:
      mode: ${{ steps.plan.outputs.mode }}
      version: ${{ steps.plan.outputs.version }}
    steps:
      - name: Check out the repository
        uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.13"

      - name: Classify the run
        id: plan
        shell: bash
        run: |
          if [ "$GITHUB_EVENT_NAME" = push ]; then
            python -I tools/release.py plan --tag "$GITHUB_REF_NAME" | tee plan.txt
          else
            python -I tools/release.py plan --dispatch | tee plan.txt
          fi
          cat plan.txt >> "$GITHUB_OUTPUT"

  # The wheels and coexist jobs of wheels.yml run inside this workflow run, so their wheel-<os> artifacts belong to it.
  wheels:
    needs: plan
    permissions:
      contents: read
    uses: ./.github/workflows/wheels.yml

  package:
    needs: [plan, wheels]
    runs-on: ubuntu-24.04
    env:
      MODE: ${{ needs.plan.outputs.mode }}
    steps:
      - name: Check out the repository
        uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.13"

      # `blender --command` still loads the executable, which needs these system libraries (tools/blender_system_deps.txt).
      - name: Install Blender's system libraries
        shell: bash
        run: sudo apt-get update && sudo apt-get install -y $(grep -v '^#' tools/blender_system_deps.txt)

      - name: Fetch Blender
        shell: bash
        run: |
          python -I tools/fetch_blender.py --version "$BLENDER_VERSION" --platform linux-x64 2>&1 | tee fetch.log
          blender_exe=$(sed -n "s/^Blender $BLENDER_VERSION executable: //p" fetch.log | tr -d '\r')
          echo "BLENDER_EXE=$blender_exe" >> "$GITHUB_ENV"

      - name: Download the wheels
        uses: actions/download-artifact@v4
        with:
          pattern: wheel-*
          path: wheelhouse
          merge-multiple: true

      - name: Build and verify the release assets
        shell: bash
        run: |
          python -I tools/release.py package --blender "$BLENDER_EXE" --wheel-dir wheelhouse \
            --out-dir dist/release --notes dist/release-notes.md --work-dir build/release

      # Two paths whose common ancestor is dist/: the artifact holds release/<assets> and release-notes.md.
      - name: Upload the release assets
        uses: actions/upload-artifact@v4
        with:
          name: release
          path: |
            dist/release/
            dist/release-notes.md
          if-no-files-found: error

      - name: Summarize
        shell: bash
        run: |
          if [ "$MODE" = dry-run ]; then
            echo "Dry run ($GITHUB_REF_NAME): every asset was built and verified; no GitHub Release is created." >> "$GITHUB_STEP_SUMMARY"
          fi
          cat dist/release-notes.md >> "$GITHUB_STEP_SUMMARY"

  # Each of INSTALL_PLATFORMS installs the zip that a user of that platform downloads, then renders the built-in
  # reference scene through it. macOS has no leg: D39 allows no macOS CI test job, and the macOS zip is built and
  # byte-verified in package.
  # `extension install-file` exits 0 even when it refuses a zip, so the registration assert of run_reference.py decides.
  install:
    name: install (${{ matrix.os }})
    needs: package
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false
      matrix:
        include:
          - os: ubuntu-24.04
            platform: linux-x64
          - os: windows-2022
            platform: windows-x64
    steps:
      - name: Check out the repository
        uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.13"

      - name: Download the release assets
        uses: actions/download-artifact@v4
        with:
          name: release
          path: dist

      - name: Install Blender's system libraries (Linux)
        if: matrix.platform == 'linux-x64'
        shell: bash
        run: sudo apt-get update && sudo apt-get install -y $(grep -v '^#' tools/blender_system_deps.txt)

      - name: Fetch Blender
        shell: bash
        env:
          PLATFORM: ${{ matrix.platform }}
        run: |
          python -I tools/fetch_blender.py --version "$BLENDER_VERSION" --platform "$PLATFORM" 2>&1 | tee fetch.log
          blender_exe=$(sed -n "s/^Blender $BLENDER_VERSION executable: //p" fetch.log | tr -d '\r')
          echo "BLENDER_EXE=$blender_exe" >> "$GITHUB_ENV"

      - name: Check Blender's shared libraries (Linux)
        if: matrix.platform == 'linux-x64'
        shell: bash
        run: |
          test -x "$BLENDER_EXE" || exit 1; deps=$(ldd "$BLENDER_EXE") || exit 1; if grep 'not found' <<<"$deps"; then exit 1; fi

      - name: Install the extension and render the reference scene
        shell: bash
        env:
          PLATFORM: ${{ matrix.platform }}
        run: |
          zip="dist/release/$(python -I tools/release.py zip-name --platform "$PLATFORM" | tr -d '\r')"
          out="$RUNNER_TEMP/install-smoke"
          mkdir -p "$out"
          export BLENDER_USER_RESOURCES="$RUNNER_TEMP/blender-user"
          "$BLENDER_EXE" --command extension install-file -r user_default -e "$zip"
          "$BLENDER_EXE" -b --factory-startup --python-exit-code 1 --python tests/blender_it/run_reference.py -- "$out"
          test -f "$out/blender.npy"
          test -f "$out/blender.json"

  # Only a v<version> tag publishes. GH_REPO names the repository, so no checkout is needed.
  publish:
    needs: [plan, package, install]
    if: needs.plan.outputs.mode == 'release'
    runs-on: ubuntu-24.04
    permissions:
      contents: write
    steps:
      - name: Download the release assets
        uses: actions/download-artifact@v4
        with:
          name: release
          path: dist

      - name: Check the asset checksums
        shell: bash
        working-directory: dist/release
        run: sha256sum -c SHA256SUMS

      - name: Create the GitHub Release
        shell: bash
        env:
          GH_TOKEN: ${{ github.token }}
          GH_REPO: ${{ github.repository }}
          VERSION: ${{ needs.plan.outputs.version }}
        run: |
          gh release create "$GITHUB_REF_NAME" --verify-tag --title "Painterly $VERSION" \
            --notes-file dist/release-notes.md dist/release/*
```
Notes for the implementer. Do not change the YAML to work around these; they are deliberate:
- `shell: bash` runs `bash -eo pipefail`, so a failing `release.py plan` fails the step even through `tee`.
- `GITHUB_EVENT_NAME`, `GITHUB_REF_NAME`, `RUNNER_TEMP` and `GITHUB_STEP_SUMMARY` are set by the runner.
- The `install` job reuses T4.4's `run_reference.py` unchanged. Its `addon_utils.enable(...)` plus the `PAINTERLY`
  registration assert is the proof that the zip installed (fact 6).
- `gh release create` fails when a release for the tag already exists. A re-run never overwrites published assets.
- Rerunning a dry-run tag is harmless: it creates nothing outside the run.
